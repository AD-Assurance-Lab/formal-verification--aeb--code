# Session 2026-08-16: first simulator run

Ten hours of exclusive CARLA access. This is what happened, including the parts that
went wrong, so the next session does not rediscover them.

Read `PROTOCOL.md` first. Nothing here changes the design; two amendments were recorded
before the simulator was touched (A1 units, A2 posted limits).

---

## The simulator will not open a window on this machine

`CarlaUE4-Linux-Shipping` exits with code 1 and **no output at all** when launched
windowed. Tried and failed: bare, `-windowed -ResX -ResY`, `-opengl`, `-vulkan`, and via
`CarlaUE4.sh`. Adding `-RenderOffScreen` starts it normally and the RPC port comes up in
about a minute.

Ruled out, so nobody repeats the search:

| Suspected | Actually |
|---|---|
| X display or auth | Session is x11, `xdpyinfo` works, and strace shows CARLA opening `/run/user/1000/gdm/Xauthority` successfully |
| Missing libraries | `ldd` clean, Vulkan loader present at `/usr/lib/x86_64-linux-gnu/libvulkan.so.1` |
| Disk full | 109 GB free |
| Vulkan ICD | `nvidia_icd.json` present, driver 580.173.02 |

It fails after X initialisation, at window creation. **Zach normally watches the CARLA
window, so running offscreen is a deviation from how he wants this run.** It was the only
mode that starts. Re-test windowed after any driver or desktop update.

Working launch:

```bash
cd /home/za/carla && ./CarlaUE4/Binaries/Linux/CarlaUE4-Linux-Shipping CarlaUE4 \
    -carla-rpc-port=3000 -RenderOffScreen -nosound -quality-level=Epic
```

Hardware note: this box has an **RTX 4070, 12 GB**. Town13 loaded sits at about 9.5 GB of
that. The 5090 is not here yet, and the verifier-scaling work assumes it.

## Town13 is viable (smoke, PASS)

The single cheapest thing that could have killed the plan did not happen. Town13 loads,
the ego tagged `role_name='hero'` accepts a camera, and 100 ticks deliver exactly 100
frames. The large-map crash that cost another project in this lab several weeks does not
reproduce with the tag.

## The survey coordinates are right, and the first check said they were not

Projecting surveyed site coordinates onto CARLA roads reported the nearest road **150 to
180 m away**, which looked like a broken coordinate frame. It was not. Town13 sits at
z about 165 m, the survey has no elevation because OpenDRIVE elevation was not parsed, and
`get_waypoint` measures in 3D. Measured horizontally the error is **1.6 to 5.3 m**, which
is the offset between a road reference line and a lane centre, exactly as expected.

The sign convention does matter: OpenDRIVE y must be negated for CARLA world y. With the
wrong sign the same points land 500 to 3,000 m away.

## Fixes made to jobs that had never been run

- **Braking settled by coasting.** `set_target_velocity` followed by two seconds of ticks
  with no throttle bleeds off several mph, so a run labelled 50 mph was not one. It now
  holds the commanded speed through the settle.
- **Destroy needs a tick.** Twenty reps spawning at the same point fail on the second one,
  because the destroy has not been applied yet.
- **The contact measure over-reached.** It used the bounding box diagonal as the reach,
  which for a head-on approach is 0.2 m too long on a passenger car. That would report
  contact before it happened and understate every standoff the study measures. Each box
  is now projected onto the line joining the two vehicles.
- **Braking measured at an arbitrary spawn point.** Now measured on a surveyed straight,
  with the grade recorded per run, because braking authority on a slope is not the
  flat-road number.

## The server was OOM-killed at 58 GB

The braking run died when the kernel killed CARLA:

```
Out of memory: Killed process 68224 (CarlaUE4-Linux-)
total-vm:71465764kB, anon-rss:58330100kB
```

Fifty-eight gigabytes resident on a 64 GB machine. That is **not** the slow leak already
recorded in the lab notes (about 10.5 GiB over 11 hours). Town13 loaded and idle sits
around 9.5 GB; it reached 58 GB inside roughly fifteen minutes of a spawn, settle, brake,
destroy loop.

This threatens the Town13 choice directly, so it is being measured rather than guessed:
`tools/probe_memory.py` runs spawn and destroy cycles and logs the server's resident
memory each cycle, on demand with rendering on or off.

Mitigation already in the code, pending that measurement: the braking, contact and oracle
jobs use no camera, so they now connect with `no_rendering_mode`. Physics is unaffected,
so this is not a quality reduction on any perception measurement, and the capture jobs
keep rendering on.

### The second crash names the cause

The next attempt did not OOM. It **segfaulted**, and the engine said why:

```
LowLevelFatalError [File:Unknown] [Line: 1214]
GameThread timed out waiting for RenderThread after 60.00 secs
Signal 11 caught.
```

The render thread stalled for a full minute and the engine killed itself. That is a
rendering problem, not a physics one, on a 12 GB RTX 4070 running a large map at Epic
quality offscreen. It also reframes the OOM: both failures are the renderer, one by
exhausting memory and one by stalling.

Which is convenient, because the braking, contact and oracle jobs need no camera at all
and already connect with `no_rendering_mode`. The open question is narrower than it
looked: physics-only work on Town13 is probably fine, and the **capture** jobs are the
ones at risk.

### Decision rule, written before the measurement

So the map choice is not rationalised after seeing the number:

| Measured growth per spawn/tick/destroy cycle | Action |
|---|---|
| Under 0.3 GB with rendering on | Town13 stands. The OOM came from something else in the braking loop, and that is the next thing to isolate |
| Large with rendering on, small with it off | Town13 stands for physics jobs, which already run with rendering off. Capture jobs get a hard cap on spawns per server start |
| Large either way | Town13 is not usable on this hardware. Move to **Town01** and record it as an amendment |

Town01 is the fallback because the 650 ft site requirement was wrong: it assumed the ego
accelerates up to test speed, and the protocol launches it at cruise speed instead. At
400 ft braking and 300 ft pedestrian, Town01 offers 9 pedestrian and 7 braking sites and
is a small map. Re-surveyed and confirmed; `tools/survey_maps.py --braking-ft --ped-ft`.

## Operational traps hit today

- **`tail` buffers.** Piping a long job's output through `tail -15` leaves the live output
  file empty until the job ends, so a healthy run looks dead. Same class as the known
  `grep` block-buffering trap. Do not pipe job output when you want progress.
- **`pgrep -f` matched the launching shell, not the server.** The first memory probe
  reported a flat 0.00 GB, which reads as "no leak" and is entirely wrong: the shell that
  launched CARLA also matches the command line, and it sorts first. Match the process
  NAME, which the kernel truncates to 15 characters, so `pgrep -x "CarlaUE4-Linux-"`.
  A measurement tool that silently measures the wrong process is worse than no tool.
- **`pkill -f` killed this session's own shell**, exit 144, even with a bracket pattern.
  Use explicit PIDs. This is already in the lab notes and it still happened.
- **One client at a time in synchronous mode.** A second script calling `get_world()`
  while a job owns the tick just times out after 60 s. Obvious in hindsight, and it looks
  exactly like a dead server. Do not probe the simulator while a measurement run is going.
- The bash wrapper collapses newlines inside `eval`, so `cmd &` followed by a newline and
  `sleep` becomes `cmd & sleep ...` on one line. Use explicit separators.

## Four measurements that changed the study

**Town13 is unusable on this hardware.** Under 0.6 ticks/s against Town01's 720 to 760,
plus an OOM kill at 58 GB and a render-thread segfault. A thousandfold speed difference
settles it even ignoring the crashes. See A3.

**Scene lighting takes 80 ticks to settle after a sun change**, not the handful that
"weather applies on the next tick" suggests. A capture 12 ticks in reads 75 percent too
bright. See A4.

**The camera defaulted to auto-exposure**, which is the defect this lab published about
ACDC, in our own captures. See A4.

**The family's interior is wrong across the horizon.** Blend against rendered is 0.243 of
full range over the full interval, 0.003 to 0.008 for an 11 degree sub-interval away from
sunrise, and 0.153 for the same width across it. See A5. This is the one with
consequences for the design rather than the plumbing.

## Bugs found, all of which produced confident wrong numbers

Listed because the pattern matters more than any one of them. Each produced output that
looked entirely reasonable.

| Bug | What it reported |
|---|---|
| Ego launched down the opposing lane | drove into a junction at 21 m/s, recorded as 4.94 g of braking authority, verdict PASS |
| Proportional-only speed hold | runs labelled 25 and 50 mph driven at 19 and 38, both exactly 76 percent |
| `except queue.Empty: pass` in the capture loop | every image belonged to the previous condition |
| 12-tick weather drain | night endpoints 75 percent too bright |
| `pgrep -f` matching the launching shell | server memory reported as a flat 0.00 GB, reading as "no leak" |

Four of the five were caught by a result that was *physically* impossible rather than by a
test. The plausibility checks now in `job_braking`, rejecting averages over 1.3 g or runs
below 90 percent of commanded speed, exist because of the first one.

## M3 groundwork, done

The illumination axis is **11 measured sub-intervals** (A6). Step size collapses from
30.25 degrees at the top of the range to 0.14 approaching the horizon and opens back up
to 25.87 past it. One sub-interval, the 0.14 degree sliver at the horizon itself, cannot
meet tolerance at any width and is declared uncovered. These knots are the frames to
render for training.

Scenario objects are built to the standard rather than approximated:

- **Trench plate.** `static.prop.ironplank` is 3.9 x 4.8 ft, a quarter of the specified
  8 x 12. Tiling edge to edge and rounding up covered 11.7 x 14.4, so tiles overlap and
  the outer edges now land on exactly 8.0 x 12.0 ft.
- **Crossing pedestrian.** Driven by direct control, not `controller.ai.walker`, which
  picks its own path and would break determinism. An apparent 8 percent speed shortfall
  was the start ramp being averaged in: in steady state the walker tracks its command
  exactly. The ramp is real though, 2.22 m/s^2 over about 13 ticks, plus a 0.49 m jump
  on the first tick from the spawn drop. Both are compensated, because for a crossing
  test the arrival time is the scenario.

**The oracle check now passes on both scenarios**, which is what makes them usable:

| scenario | perfect oracle | late oracle |
|---|---|---|
| stationary lead vehicle | 10/10, 5.0 ft standoff | 0/10, contact at -0.3 ft |
| crossing pedestrian | 10/10, 6.1 ft standoff | 0/10, contact at -2.8 ft |

One pedestrian run returned 6.1 ft where the others gave 4.1, a single-tick difference in
the release trigger and the only run-to-run variation seen all session. Both outcomes
pass, and it is worth knowing the harness is not bit-identical when a walker is involved.

## The capture route works, on the easy case

Verification runs on frames captured by placing the ego at a pose rather than driving it
there. If those do not reproduce what the vehicle sees, sound bounds on them prove
nothing. Measured over five poses: placement error **0.000 m**, image difference **0.0065
to 0.0078** normalised, which is about what separates a moving frame from a stationary
one.

Two honest caveats. This is the image version; the gate that decides compares policy
output and waits for a policy. And elevation is what broke the parent study's captures,
while Town01's site is 0.0 percent grade, so this is the easy case and it should be
re-run if the study ever moves to a site with a gradient.

## M3 done, and the safety budget validated by accident

The expert passes **10/10 at daylight and 10/10 at darkness with lower beam**, with
rendering on and a camera attached, which is the configuration collection will use.

Getting there produced the nicest result of the session. An agreement check between the
two endpoints reported them as DIFFERENT. Chasing it:

- One run in ten returns a standoff of 3.32 ft where the others return 4.99.
- The difference, 1.67 ft, is **one control tick of travel** at 25 mph: 11.18 m/s times
  0.05 s is 0.56 m, which is 1.83 ft. The brake trigger is a threshold evaluated once per
  tick, so whether it fires on tick N or N+1 shifts the whole stop by that much.
- The required standoff is **3.28 ft** and the worst observed is **3.32 ft**.

So the worst case clears the requirement by four hundredths of a foot, and the reason is
that `r_req` contains a `v * dt` term for exactly this quantisation. The budget reserves
one tick, and one tick is precisely what the variation turns out to be. A tight correct
budget looks like this: it passes, barely, for a stated reason.

Two false alarms on the way, both mine. An exact-equality check called 3 mm of noise a
lighting effect, and a 0.1 ft tolerance would have done the same. The tolerance is now
one tick of travel, derived rather than picked.
